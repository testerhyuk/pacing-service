# 저장소 장애 처리 정책

## 1. 목적

페이싱 판단과 예산 예약은 Redis의 실시간 상태에 의존한다. Redis 또는 PostgreSQL에 접근할 수 없는 상황에서 잘못된 PASS를 반환하거나 예산을 이중 예약하지 않도록, 실패 응답과 재시도 및 관측 정책을 하나의 계약으로 정의한다.

## 2. 기본 원칙

- 저장소 장애를 정상적인 BLOCK이나 예산 부족으로 숨기지 않는다.
- 저장소 장애 시 API는 `503 Service Unavailable`과 `STORAGE_UNAVAILABLE`을 반환한다.
- API 서버 내부에서는 저장소 작업을 재시도하지 않는다.
- 예산 예약은 PostgreSQL로 우회하지 않는다. Redis의 예산 검사와 예약액 증가가 원자적으로 완료된 경우에만 성공한다.
- 광고 노출은 예산 예약 성공 이후에만 허용한다.

## 3. API별 동작

### 3.1 페이싱 판단

Redis 또는 PostgreSQL 접근에 실패하면 판단 결과를 임의로 PASS/BLOCK으로 만들지 않고 다음 응답을 반환한다.

```json
{
  "code": "STORAGE_UNAVAILABLE",
  "message": "저장소에 일시적으로 접근할 수 없습니다",
  "timestamp": "2026-08-13T00:00:00Z",
  "path": "/internal/v1/pacing/decisions/decide"
}
```

호출 서비스는 해당 광고를 현재 경매 후보에서 제외하고 아래 재시도 계약에 따라 다시 요청한다.

### 3.2 예산 예약

Redis 또는 PostgreSQL 접근에 실패하면 `503 STORAGE_UNAVAILABLE`을 반환한다. PostgreSQL만 사용하여 예약을 성공 처리하지 않는다. Redis를 우회하면 동시 요청 사이에서 전체·일일 예산 초과를 막는 원자성이 사라지기 때문이다.

호출 서비스는 예약 성공 응답을 받기 전까지 광고를 노출하지 않는다.

## 4. 외부 호출자 재시도 계약

- 최초 요청 실패 후 최대 2회 재시도한다. 전체 시도 횟수는 최초 요청을 포함해 최대 3회다.
- 첫 번째 재시도는 약 100ms 후, 두 번째 재시도는 약 200ms 후 수행한다.
- 각 지연 시간에 0~50ms의 무작위 지연을 더해 동시 재시도 집중을 줄인다.
- 페이싱 판단은 최초 요청과 동일한 `requestId`를 사용한다.
- 예산 예약은 최초 요청과 동일한 `reservationId`를 사용한다.
- HMAC의 `timestamp`와 `nonce`는 매 요청마다 새로 생성한다. 이전 값을 재사용하면 재전송 공격 방지 정책에 의해 거절된다.
- 두 번의 재시도까지 실패하면 해당 요청 처리를 종료하고 상위 시스템의 실패 정책을 적용한다.

`STORAGE_UNAVAILABLE` 오류 코드 자체를 재시도 가능 신호로 사용한다. 별도의 `retryable` 필드는 추가하지 않는다. `Retry-After` 헤더도 사용하지 않는다. 표준 `Retry-After`는 초 단위 또는 날짜만 표현하므로 100~200ms 재시도 계약을 정확히 전달할 수 없기 때문이다.

## 5. 관측 정책

### 5.1 메트릭

모든 저장소 접근 실패를 다음 카운터에 기록한다.

```text
pacing_api_storage_failure_total{storage, operation}
```

장애 후 첫 성공은 다음 카운터에 기록한다.

```text
pacing_api_storage_recovery_total{storage, operation}
```

`storage`는 `REDIS`, `POSTGRESQL`, `UNKNOWN` 중 하나다. `operation`은 `AUTHENTICATION`, `DECISION`, `RESERVATION`, `ADMIN` 중 하나다.

### 5.2 로그 제한과 복구 로그

- 같은 `storage`와 `operation` 조합의 첫 실패는 스택 트레이스와 함께 즉시 기록한다.
- 동일 장애가 반복되면 30초 동안 스택 트레이스를 다시 기록하지 않는다.
- 30초가 지난 후에도 장애가 계속되면 누적 실패 수와 생략된 로그 수를 포함해 다시 기록한다.
- 장애 이후 첫 성공 시 복구 시각, 장애 지속 시간, 장애 중 누적 실패 수를 한 번 기록한다.
- 로그를 제한해도 실패 메트릭은 한 건도 생략하지 않는다.

로그 제한 주기는 다음 환경변수로 변경할 수 있다.

```text
PACING_STORAGE_FAILURE_LOG_INTERVAL=30s
```

### 5.3 Prometheus 알림

- 최근 1분 저장소 실패율이 1%를 초과하고 10% 이하이면 `warning`을 발생시킨다.
- 최근 1분 저장소 실패율이 10%를 초과하면 `critical`을 발생시킨다.
- warning과 critical 조건을 분리해 동일 장애로 두 알림이 동시에 발생하지 않게 한다.

## 6. 정책 결정 이유

### 서버 내부 재시도를 하지 않는 이유

API 인스턴스가 요청마다 저장소 재시도를 수행하면 장애 중인 저장소에 부하를 더하고 요청 스레드를 오래 점유한다. 호출자가 짧은 지연과 jitter를 적용해 재시도하도록 책임을 분리했다.

### 예약에서 PostgreSQL fallback을 사용하지 않는 이유

예산 예약은 Redis Lua 스크립트가 예산 검사, 중복 확인, 예약액 증가를 하나의 원자적 작업으로 처리한다. PostgreSQL fallback은 같은 동시성 보장을 제공하지 않으므로 예산 초과 가능성을 만든다. 따라서 안전하게 실패하고 같은 `reservationId`로 재시도한다.

### 오류 코드만으로 재시도 여부를 전달하는 이유

현재 내부 호출자에게 필요한 판단은 `STORAGE_UNAVAILABLE`인지 여부다. 응답에 같은 의미의 boolean 필드를 추가하면 두 값이 불일치할 가능성만 늘어난다. 오류 코드 계약을 단일 기준으로 사용한다.

## 7. 이번 범위에서 제외한 항목

Circuit Breaker는 후속 개선으로 남긴다. 현재 범위에서는 빠른 저장소 타임아웃, 명확한 503 응답, 외부 재시도 제한, 실패율 알림과 로그 억제로 장애 확산을 통제한다.
